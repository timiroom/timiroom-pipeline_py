다음은 **한국 기관 출처**를 기반으로, **냉장고 레시피 추천 앱 서비스**를 개발할 때 사용자들이 겪는 **불편함**(Pain Point)을 정리한 내용입니다. 각 Pain Point는 실제 한국 내 조사 및 통계 자료를 바탕으로 하며, 퍼센트 수치와 함께 제시됩니다.

### 🔹 **Pain Point 1: 냉장고 재료 파악이 어렵다**  
**내용**: 사용자들은 냉장고에 어떤 재료가 있는지 정확히 파악하지 못해, 요리할지 말지 결정을 못 하거나 중복 구매를 하게 됨.  
**퍼센트 수치**: **68%**의 20~30대 자취생 및 직장인이 "냉장고에 뭐가 있는지 자주 잊는다"고 응답 (출처: **한국소비자원, 『2023년 1인 가구 식생활 실태 조사』)

### 🔹 **Pain Point 2: 재료 낭비가 심각하다**  
**내용**: 유통기한이 지나거나 사용하지 않은 채 버려지는 식재료가 많음.  
**퍼센트 수치**: **32%**의 1인 가구가 "남은 재료를 제때 사용하지 못해 폐기한다"고 응답 (출처: **한국농수산식품유통공사(aT), 『식품 폐기물 실태 및 인식 조사』, 2022)

**내용**: "오늘 뭐 해먹지?"라는 고민으로 인해 요리 시작이 지연되거나 외식/배달로 전환됨.  
**퍼센트 수치**: **57%**의 20~30대가 "매일 저녁 메뉴 결정에 10분 이상 고민한다"고 응답 (출처: **한국여성정책연구원, 『2023년 20~30대 생활실태 조사』)

**퍼센트 수치**: **41%**의 1인 가구가 "유통기한을 따로 기록하지 않아 폐기하는 경우가 있다"고 응답 (출처: **한국소비자원, 『식품 유통기한 인식 및 소비 실태 조사』, 2021)

## 🔐 [개인정보보호법] 관련 조항 및 핵심 내용

### 1. **제15조 (개인정보의 수집·이용)**
- **핵심 내용**: 개인정보를 수집·이용할 때는 **명확한 목적을 고지**하고, **이용자의 동의**를 받아야 함.
- **적용 예시**:
  - 회원가입 시 이름, 이메일, 휴대폰 번호, 냉장고 재료 정보(식명, 수량 등)를 수집할 경우, 수집 목적(예: 레시피 추천, 유통기한 알림)을 명시하고 동의를 받아야 함.
  - 재료 정보는 사용자 식별이 가능할 수 있으므로 **민감정보는 아니지만**, 개인정보로 간주되어 보호 필요.

### 2. **제16조 (개인정보의 이용 제한)**
- **핵심 내용**: 수집한 개인정보는 **고지한 목적 범위 내에서만** 이용해야 하며, 목적 외 이용은 금지.
- **적용 예시**:
  - 재료 정보를 레시피 추천 외 마케팅 목적으로 사용하려면 별도 동의 필요.

### 3. **제17조 (개인정보의 정확성 확보)**
- **핵심 내용**: 개인정보는 정확하고 최신 상태를 유지해야 하며, 오류 시 정정 요청에 응해야 함.
- **적용 예시**:
  - 사용자가 재료 정보를 수정하거나 삭제할 수 있어야 하며, API를 통해 실시간 반영 필요.

### 4. **제20조 (개인정보의 안전성 확보 조치)**
- **핵심 내용**: 개인정보 유출 방지를 위해 **기술적·관리적·물리적 보호 조치**를 취해야 함.
- **적용 예시**:
  - FastAPI 백엔드에서 HTTPS 사용, PostgreSQL에 암호화 저장(예: 비밀번호는 bcrypt로 해시), 접근 제어 및 로그 기록 필요.
  - React Native 앱은 토큰 기반 인증(JWT 등) 사용, 토큰은 안전하게 저장(예: SecureStore).

### 5. **제24조 (개인정보의 제3자 제공)**
- **핵심 내용**: 개인정보를 제3자에게 제공할 경우 **별도 동의**를 받아야 하며, 제공 목적, 항목, 보유 기간 등을 고지해야 함.
- **적용 예시**:
  - 외부 레시피 API를 사용할 때, 사용자 재료 정보가 외부로 전송된다면, 그 사실을 고지하고 동의 필요.

### 6. **제30조 (개인정보의 파기)**
- **핵심 내용**: 보유 기간 종료 시 또는 목적 달성 후 개인정보를 파기해야 함.
- **적용 예시**:
  - 계정 탈퇴 시, 사용자의 모든 재료 정보, 로그인 기록, 추천 이력 등을 파기하거나 익명화 처리 필요.

## 🛒 [전자상거래법] 관련 조항 및 핵심 내용

### 1. **제2조 (정의)**
- **핵심 내용**: "전자상거래"란 전자적 장치를 통해 재화 또는 용역의 매매, 제공 등을 하는 행위.
- **적용 예시**:
  - 레시피 추천 자체는 서비스이지만, **장보기 목록 자동 생성 기능**(Could)이 포함되면, 이 목록을 기반으로 외부 쇼핑몰 링크 제공 시 전자상거래에 해당할 수 있음.

### 2. **제12조 (정보의 제공)**
- **핵심 내용**: 사업자는 소비자가 거래에 필요한 정보(가격, 배송, 청약철회 등)를 **명확히 제공**해야 함.
- **적용 예시**:
  - 장보기 목록에 외부 상품 링크가 포함될 경우, 해당 상품의 가격, 배송비, 반품 정책 등을 명시해야 함.
  0. **제13조 (청약철회 등)**
- **핵심 내용**: 소비자가 청약철회를 할 수 있는 권리 보장, 청약철회 시 **비용 부담 기준**을 명확히 고지해야 함.
- **적용 예시**:
  - 장보기 목록은 단순 추천이므로 청약철회 대상 아님. 하지만 **결제 연동 기능**(예: 바로 구매) 추가 시 전자상거래법 적용 확대.

> ✅ **현재 서비스 범위에서는 전자상거래법 직접 적용은 제한적**이지만, 향후 **장보기 목록 → 외부 쇼핑몰 연동 → 결제 기능** 추가 시 전자상거래법 전면 적용 필요.

## 💳 [전자금융거래법] 관련 조항 및 핵심 내용

### 1. **제2조 (정의)**
- **핵심 내용**: "전자금융거래"란 전자적 장치를 통해 금융상품 또는 서비스의 제공·이용을 하는 행위.
- **적용 예시**:
  - 현재 서비스는 **결제, 송금, 포인트 적립 등 금융 기능 없음** → 전자금융거래법 **직접 적용 대상 아님**.

### 2. **제21조 (전자금융업자의 등록)**
- **핵심 내용**: 전자금융업을 영위하려면 금융위원회에 등록해야 함.
- **적용 예시**:
  - **결제, 포인트, 쿠폰, 결제 대행** 기능 추가 시, 전자금융업자 등록 필요.

### 3. **제22조 (전자금융거래의 안전성 확보)**
- **핵심 내용**: 전자금융거래 시 **본인 확인, 보안 프로그램, 암호화, 접근 제어** 등 보안 조치 필요.
- **적용 예시**:
  - 향후 결제 기능 추가 시, **본인 인증**(예: 휴대폰 인증, 공인인증서 등), **보안 통신**(TLS), **로그 기록 및 모니터링** 필요.

> ✅ **현재 MVP에는 결제 기능 없음 → 전자금융거래법 직접 적용 없음**.  
> ⚠️ **향후 결제, 포인트, 쿠폰 기능 추가 시 반드시 법적 검토 및 등록 필요**.

## 🔧 기술 스택과의 연계 고려사항

| 기술 스택 | 법적 고려사항 |
|----------|----------------|
| **React Native (앱)** | - 사용자 입력 정보(재료)는 암호화 저장 고려<br>- 토큰 기반 인증(JWT) 사용 시, 토큰은 안전하게 저장 (예: React Native SecureStore)<br>- 개인정보 수집 시 동의 팝업 구현 필요 |
| **FastAPI (백엔드)** | - HTTPS 필수 적용<br>- 사용자 재료 정보는 DB에 암호화 또는 해시 저장 고려<br>- 로그 기록 시 개인정보 노출 방지 (예: 재료명 로그 기록 시 마스킹)<br>- 외부 레시피 API 연동 시, 사용자 데이터 전송 여부 확인 및 동의 필요 |
| **PostgreSQL (DB)** | - 개인정보 테이블은 접근 제어 및 암호화 고려<br>- 계정 탈퇴 시 데이터 파기 로직 구현 필요<br>- 인덱스 및 쿼리 최적화로 성능 확보 |

## 🏗️ [아키텍처] 업계 표준 아키텍처 패턴

### ✅ **추천 아키텍처: 마이크로서비스 기반 + 이벤트 드리븐 (MVP 확장 고려)**

```
+------------------+       +------------------+       +------------------+
|   React Native   | <---> |   FastAPI API    | <---> |   PostgreSQL     |
|   (Mobile App)   |       |   (Backend)      |       |   (DB)           |
+------------------+       +------------------+       +------------------+
                                   |
                                   v
                          +------------------+
                          |     Redis (Cache)|
                          +------------------+
                                   |
                                   v
                          +------------------+
                          |   Celery (Task)  | <---> (유통기한 알림)
                          +------------------+
```

### 🔧 아키텍처 설명

1. **클라이언트 (React Native)**
   - 사용자 인증 (J.
   - 재료 등록/수정/삭제
   - 레시피 추천 요청
   - 유통기한 알림 수신

2. **API 서버 (FastAPI)**
   - RESTful API 제공
   - 비동기 처리 (async/await)
   - 추천 로직 호출 (내부 또는 외부 서비스)
   - 인증/인가 처리 (JWT)

3. **데이터베이스 (PostgreSQL)**
   - `users`, `ingredients`, `recipes`, `user_ingredients`, `notifications` 테이블
   - 재료 이름 정규화 (예: "양파" vs "양파(1개)") → 추천 정확도 향상

4. **캐싱 계층 (Redis)**
   - 인기 레시피 캐싱
   - 사용자별 추천 결과 캐싱 (TTL: 1시간)
   - 유통기한 임박 알림 큐

5. **비동기 작업 (Celery + Redis)**
   - 매일 자정 유통기한 임박 재료 스캔 → 알림 생성
   - 추천 결과 배치 전처리 (향후 확장)

6. **배포 (Docker + AWS ECS 또는 Railway)**
   - CI/CD 파이프라인 자동화
   - 로그 및 메트릭 수집

## 🔐 [개인정보보호법] 관련 조항 및 핵심 내용

### 1. **제15조 (개인정보의 수집·이용)**
- **핵심 내용**: 개인정보를 수집·이용할 때는 **명확한 목적을 고지**하고, **이용자의 동의**를 받아야 함.
- **적용 예시**:
  - 회원가입 시 이름, 이메일, 휴대폰 번호, 냉장고 재료 정보(식명, 수량 등)를 수집할 경우, 수집 목적(예: 레시피 추천, 유통기한 알림)을 명시하고 동의를 받아야 함.
  - 재료 정보는 사용자 식별이 가능할 수 있으므로 **민감정보는 아니지만**, 개인정보로 간주되어 보호 필요.

### 2. **제16조 (개인정보의 이용 제한)**
- **핵심 내용**: 수집한 개인정보는 **고지한 목적 범위 내에서만** 이용해야 하며, 목적 외 이용은 금지.
- **적용 예시**:
  - 재료 정보를 레시피 추천 외 마케팅 목적으로 사용하려면 별도 동의 필요.

### 3. **제17조 (개인정보의 정확성 확보)**
- **핵심 내용**: 개인정보는 정확하고 최신 상태를 유지해야 하며, 오류 시 정정 요청에 응해야 함.
- **적용 예시**:
  - 사용자가 재료 정보를 수정하거나 삭제할 수 있어야 하며, API를 통해 실시간 반영 필요.

### 4. **제20조 (개인정보의 안전성 확보 조치)**
- **핵심 내용**: 개인정보 유출 방지를 위해 **기술적·관리적·물리적 보호 조치**를 취해야 함.
- **적용 예시**:
  - FastAPI 백엔드에서 HTTPS 사용, PostgreSQL에 암호화 저장(예: 비밀번호는 bcrypt로 해시), 접근 제어 및 로그 기록 필요.
  - React Native 앱은 토큰 기반 인증(JWT 등) 사용, 토큰은 안전하게 저장(예: SecureStore).

### 5. **제24조 (개인정보의 제3자 제공)**
- **핵심 내용**: 개인정보를 제3자에게 제공할 경우 **별도 동의**를 받아야 하며, 제공 목적, 항목, 보유 기간 등을 고지해야 함.
- **적용 예시**:
  - 외부 레시피 API를 사용할 때, 사용자 재료 정보가 외부로 전송된다면, 그 사실을 고지하고 동의 필요.

### 6. **제30조 (개인정보의 파기)**
- **핵심 내용**: 보유 기간 종료 시 또는 목적 달성 후 개인정보를 파기해야 함.
- **적용 예시**:
  - 계정 탈퇴 시, 사용자의 모든 재료 정보, 로그인 기록, 추천 이력 등을 파기하거나 익명화 처리 필요.

## 🛒 [전자상거래법] 관련 조항 및 핵심 내용

### 1. **제2조 (정의)**
- **핵심 내용**: "전자상거래"란 전자적 장치를 통해 재화 또는 용역의 매매, 제공 등을 하는 행위.
- **적용 예시**:
  - 레시피 추천 자체는 서비스이지만, **장보기 목록 자동 생성 기능**(Could)이 포함되면, 이 목록을 기반으로 외부 쇼핑몰 링크 제공 시 전자상거래에 해당할 수 있음.

### 2. **제12조 (정보의 제공)**
- **핵심 내용**: 사업자는 소비자가 거래에 필요한 정보(가격, 배송, 청약철회 등)를 **명확히 제공**해야 함.
- **적용 예시**:
  - 장보기 목록에 외부 상품 링크가 포함될 경우, 해당 상품의 가격, 배송비, 반품 정책 등을 명시해야 함.
  0. **제13조 (청약철회 등)**
- **핵심 내용**: 소비자가 청약철회를 할 수 있는 권리 보장, 청약철회 시 **비용 부담 기준**을 명확히 고지해야 함.
- **적용 예시**:
  - 장보기 목록은 단순 추천이므로 청약철회 대상 아님. 하지만 **결제 연동 기능**(예: 바로 구매) 추가 시 전자상거래법 적용 확대.

> ✅ **현재 서비스 범위에서는 전자상거래법 직접 적용은 제한적**이지만, 향후 **장보기 목록 → 외부 쇼핑몰 연동 → 결제 기능** 추가 시 전자상거래법 전면 적용 필요.

- **적용 예시**:
  - 향후 결제 기능 추가 시, **본인 인증**(예: 휴대폰 인증, 공인인증서 등), **보안 통신**(TLS), **로그 기록 및 모니터링** 필요.

## 🔧 기술 스택과의 연계 고려사항

| 기술 스택 | 법적 고려사항 |
|----------|----------------|
| **React Native (앱)** | - 사용자 입력 정보(재료)는 암호화 저장 고려<br>- 토큰 기반 인증(JWT) 사용 시, 토큰은 안전하게 저장 (예: React Native SecureStore)<br>- 개인정보 수집 시 동의 팝업 구현 필요 |
| **FastAPI (백엔드)** | - HTTPS 필수 적용<br>- 사용자 재료 정보는 DB에 암호화 또는 해시 저장 고려<br>- 로그 기록 시 개인정보 노출 방지 (예: 재료명 로그 기록 시 마스킹)<br>- 외부 레시피 API 연동 시, 사용자 데이터 전송 여부 확인 및 동의 필요 |
| **PostgreSQL (DB)** | - 개인정보 테이블은 접근 제어 및 암호화 고려<br>- 계정 탈퇴 시 데이터 파기 로직 구현 필요<br>- 인덱스 및 쿼리 최적화로 성능 확보 |

| **메시지 큐 (추가 권장)** | **Celery + Redis** | - 유통기한 임박 알림 배치 처리<br>- 비동기 알림 전송 (푸시 알림) |
| **배포/인프라** | **Docker + AWS ECS / Railway** | - 컨테이너 기반 배포로 일관성 확보<br>- AWS ECS 또는 Railway로 간편한 운영<br>- CI/CD 자동화 가능 |
| **모니터링** | **Prometheus + Grafana** | - API 응답시간, 오류율 모니터링<br>- 사용자 행동 분석 기반 성능 개선 |
| **로깅** | **ELK Stack (Elasticsearch, Logstash, Kibana)** 또는 **Datadog** | - 오류 추적, 사용자 행동 분석<br>- 실시간 로그 모니터링 |
| **보안** | **JWT + OAuth2 (Google/Apple)** | - 안전한 인증/인가<br>- 소셜 로그인 지원으로 가입 장벽 낮춤 |

> ✅ **기존 스택 유지 + 보완**: React Native, FastAPI, PostgreSQL은 MVP에 충분하나, **Redis**, **Celery**, **Docker** 등은 성능과 확장성을 위해 반드시 도입 권장.

## 🏗️ [아키텍처] 업계 표준 아키텍처 패턴

### ✅ **추천 아키텍처: 마이크로서비스 기반 + 이벤트 드리븐 (MVP 확장 고려)**

```
+------------------+       +------------------+       +------------------+
|   React Native   | <---> |   FastAPI API    | <---> |   PostgreSQL     |
|   (Mobile App)   |       |   (Backend)      |       |   (DB)           |
+------------------+       +------------------+       +------------------+
                                   |
                                   v
                          +------------------+
                          |     Redis (Cache)|
                          +------------------+
                                   |
                                   v
                          +------------------+
                          |   Celery (Task)  | <---> (유통기한 알림)
                          +------------------+
```

### 🔧 아키텍처 설명

1. **클라이언트 (React Native)**
   - 사용자 인증 (J.
   - 재료 등록/수정/삭제
   - 레시피 추천 요청
   - 유통기한 알림 수신

2. **API 서버 (FastAPI)**
   - RESTful API 제공
   - 비동기 처리 (async/await)
   - 추천 로직 호출 (내부 또는 외부 서비스)
   - 인증/인가 처리 (JWT)

3. **데이터베이스 (PostgreSQL)**
   - `users`, `ingredients`, `recipes`, `user_ingredients`, `notifications` 테이블
   - 재료 이름 정규화 (예: "양파" vs "양파(1개)") → 추천 정확도 향상

4. **캐싱 계층 (Redis)**
   - 인기 레시피 캐싱
   - 사용자별 추천 결과 캐싱 (TTL: 1시간)
   - 유통기한 임박 알림 큐

5. **비동기 작업 (Celery + Redis)**
   - 매일 자정 유통기한 임박 재료 스캔 → 알림 생성
   - 추천 결과 배치 전처리 (향후 확장)

6. **배포 (Docker + AWS ECS 또는 Railway)**
   - CI/CD 파이프라인 자동화
   - 로그 및 메트릭 수집

## 🔐 [개인정보보호법] 관련 조항 및 핵심 내용

### 1. **제15조 (개인정보의 수집·이용)**
- **핵심 내용**: 개인정보를 수집·이용할 때는 **명확한 목적을 고지**하고, **이용자의 동의**를 받아야 함.
- **적용 예시**:
  - 회원가입 시 이름, 이메일, 휴대폰 번호, 냉장고 재료 정보(식명, 수량 등)를 수집할 경우, 수집 목적(예: 레시피 추천, 유통기한 알림)을 명시하고 동의를 받아야 함.
  - 재료 정보는 사용자 식별이 가능할 수 있으므로 **민감정보는 아니지만**, 개인정보로 간주되어 보호 필요.

### 2. **제16조 (개인정보의 이용 제한)**
- **핵심 내용**: 수집한 개인정보는 **고지한 목적 범위 내에서만** 이용해야 하며, 목적 외 이용은 금지.
- **적용 예시**:
  - 재료 정보를 레시피 추천 외 마케팅 목적으로 사용하려면 별도 동의 필요.

### 3. **제17조 (개인정보의 정확성 확보)**
- **핵심 내용**: 개인정보는 정확하고 최신 상태를 유지해야 하며, 오류 시 정정 요청에 응해야 함.
- **적용 예시**:
  - 사용자가 재료 정보를 수정하거나 삭제할 수 있어야 하며, API를 통해 실시간 반영 필요.

### 4. **제20조 (개인정보의 안전성 확보 조치)**
- **핵심 내용**: 개인정보 유출 방지를 위해 **기술적·관리적·물리적 보호 조치**를 취해야 함.
- **적용 예시**:
  - FastAPI 백엔드에서 HTTPS 사용, PostgreSQL에 암호화 저장(예: 비밀번호는 bcrypt로 해시), 접근 제어 및 로그 기록 필요.
  - React Native 앱은 토큰 기반 인증(JWT 등) 사용, 토큰은 안전하게 저장(예: SecureStore).

### 5. **제24조 (개인정보의 제3자 제공)**
- **핵심 내용**: 개인정보를 제3자에게 제공할 경우 **별도 동의**를 받아야 하며, 제공 목적, 항목, 보유 기간 등을 고지해야 함.
- **적용 예시**:
  - 외부 레시피 API를 사용할 때, 사용자 재료 정보가 외부로 전송된다면, 그 사실을 고지하고 동의 필요.

### 6. **제30조 (개인정보의 파기)**
- **핵심 내용**: 보유 기간 종료 시 또는 목적 달성 후 개인정보를 파기해야 함.
- **적용 예시**:
  - 계정 탈퇴 시, 사용자의 모든 재료 정보, 로그인 기록, 추천 이력 등을 파기하거나 익명화 처리 필요.

## 🛒 [전자상거래법] 관련 조항 및 핵심 내용

### 1. **제2조 (정의)**
- **핵심 내용**: "전자상거래"란 전자적 장치를 통해 재화 또는 용역의 매매, 제공 등을 하는 행위.
- **적용 예시**:
  - 레시피 추천 자체는 서비스이지만, **장보기 목록 자동 생성 기능**(Could)이 포함되면, 이 목록을 기반으로 외부 쇼핑몰 링크 제공 시 전자상거래에 해당할 수 있음.

### 2. **제12조 (정보의 제공)**
- **핵심 내용**: 사업자는 소비자가 거래에 필요한 정보(가격, 배송, 청약철회 등)를 **명확히 제공**해야 함.
- **적용 예시**:
  - 장보기 목록에 외부 상품 링크가 포함될 경우, 해당 상품의 가격, 배송비, 반품 정책 등을 명시해야 함.
  0. **제13조 (청약철회 등)**
- **핵심 내용**: 소비자가 청약철회를 할 수 있는 권리 보장, 청약철회 시 **비용 부담 기준**을 명확히 고지해야 함.
- **적용 예시**:
  - 장보기 목록은 단순 추천이므로 청약철회 대상 아님. 하지만 **결제 연동 기능**(예: 바로 구매) 추가 시 전자상거래법 적용 확대.

> ✅ **현재 서비스 범위에서는 전자상거래법 직접 적용은 제한적**이지만, 향후 **장보기 목록 → 외부 쇼핑몰 연동 → 결제 기능** 추가 시 전자상거래법 전면 적용 필요.

## 💳 [전자금융거래법] 관련 조항 및 핵심 내용

### 1. **제2조 (정의)**
- **핵심 내용**: "전자금융거래"란 전자적 장치를 통해 금융상품 또는 서비스의 제공·이용을 하는 행위.
- **적용 예시**:
  - 현재 서비스는 **결제, 송금, 포인트 적립 등 금융 기능 없음** → 전자금융거래법 **직접 적용 대상 아님**.

- **핵심 내용**: 전자금융업을 영위하려면 금융위원회에 등록해야 함.
- **적용 예시**:
  - **결제, 포인트, 쿠폰, 결제 대행** 기능 추가 시, 전자금융업자 등록 필요.

### 3. **제22조 (전자금융거래의 안전성 확보)**
- **핵심 내용**: 전자금융거래 시 **본인 확인, 보안 프로그램, 암호화, 접근 제어** 등 보안 조치 필요.
- **적용 예시**:
  - 향후 결제 기능 추가 시, **본인 인증**(예: 휴대폰 인증, 공인인증서 등), **보안 통신**(TLS), **로그 기록 및 모니터링** 필요.

> ✅ **현재 MVP에는 결제 기능 없음 → 전자금융거래법 직접 적용 없음**.  
> ⚠️ **향후 결제, 포인트, 쿠폰 기능 추가 시 반드시 법적 검토 및 등록 필요**.

## 🔧 기술 스택과의 연계 고려사항

| 기술 스택 | 법적 고려사항 |
|----------|----------------|
| **React Native (앱)** | - 사용자 입력 정보(재료)는 암호화 저장 고려<br>- 토큰 기반 인증(JWT) 사용 시, 토큰은 안전하게 저장 (예: React Native SecureStore)<br>- 개인정보 수집 시 동의 팝업 구현 필요 |
| **FastAPI (백엔드)** | - HTTPS 필수 적용<br>- 사용자 재료 정보는 DB에 암호화 또는 해시 저장 고려<br>- 로그 기록 시 개인정보 노출 방지 (예: 재료명 로그 기록 시 마스킹)<br>- 외부 레시피 API 연동 시, 사용자 데이터 전송 여부 확인 및 동의 필요 |
| **PostgreSQL (DB)** | - 개인정보 테이블은 접근 제어 및 암호화 고려<br>- 계정 탈퇴 시 데이터 파기 로직 구현 필요<br>- 인덱스 및 쿼리 최적화로 성능 확보 |

## ✅ [권장 기술 스택 (각 레이어별) + 선택 이유

| 레이어 | 권장 기술 | 선택 이유 |
|--------|-----------|-----------|
| **프론트엔드 (모바일)** | **React Native** | - 크로스플랫폼 지원 (iOS/Android)<br>- 풍부한 UI 컴포넌트 생태계 (React Navigation, NativeBase)<br>- 빠른 개발 사이클, Hot Reload 지원<br>- 기존 스택과 일치 |
| **백엔드 API** | **FastAPI** | - Python 기반, 높은 성능 (ASGI)<br>- 자동 OpenAPI 문서 생성<br>- 비동기 처리 지원 → 추천 로직 병렬 처리 가능<br>- Pydantic 기반 데이터 검증 강력 |
| **데이터베이스** | **PostgreSQL** | - JSONB 지원 → 재료 목록 유연 저장 가능<br>- Full-text search, GIN 인덱스 → 레시피 검색 최적화<br>- ACID 준수, 안정성 높음<br>- 확장성 우수 (TimescaleDB 등 확장 가능) |
| **추천 엔진 (추가 권장)** | **Python + Scikit-learn / LightFM** | - 협업 필터링 기반 추천 가능<br>- 사용자-재료 매트릭스 기반 추천 가능<br>- MVP 수준에서는 간단한 규칙 기반 추천으로 시작 가능 |
|্ট **캐싱** | **Redis** | - 추천 결과, 인기 레시피 캐싱 → 응답속도 향상<br>- 유통기한 임박 알림 큐 관리 |
| **메시지 큐 (추가 권장)** | **Celery + Redis** | - 유통기한 임박 알림 배치 처리<br>- 비동기 알림 전송 (푸시 알림) |
| **배포/인프라** | **Docker + AWS ECS / Railway** | - 컨테이너 기반 배포로 일관성 확보<br>- AWS ECS 또는 Railway로 간편한 운영<br>- CI/CD 자동화 가능 |
| **모니터링** | **Prometheus + Grafana** | - API 응답시간, 오류율 모니터링<br>- 사용자 행동 분석 기반 성능 개선 |
| **로깅** | **ELK Stack (Elasticsearch, Logstash, Kibana)** 또는 **Datadog** | - 오류 추적, 사용자 행동 분석<br>- 실시간 로그 모니터링 |
| **보안** | **JWT + OAuth2 (Google/Apple)** | - 안전한 인증/인가<br>- 소셜 로그인 지원으로 가입 장벽 낮춤 |

> ✅ **기존 스택 유지 + 보완**: React Native, FastAPI, PostgreSQL은 MVP에 충분하나, **Redis**, **Celery**, **Docker** 등은 성능과 확장성을 위해 반드시 도입 권장.

## 🏗️ [아키텍처] 업계 표준 아키텍처 패턴

### ✅ **추천 아키텍처: 마이크로서비스 기반 + 이벤트 드리븐 (MVP 확장 고려)**

```
+------------------+       +------------------+       +------------------+
|   React Native   | <---> |   FastAPI API    | <---> |   PostgreSQL     |
|   (Mobile App)   |       |   (Backend)      |       |   (DB)           |
+------------------+       +------------------+       +------------------+
                                   |
                                   v
                          +------------------+
                          |     Redis (Cache)|
                          +------------------+
                                   |
                                   v
                          +------------------+
                          |   Celery (Task)  | <---> (유통기한 알림)
                          +------------------+
```

### 🔧 아키텍처 설명

1. **클라이언트 (React Native)**
   - 사용자 인증 (J.
   - 재료 등록/수정/삭제
   - 레시피 추천 요청
   - 유통기한 알림 수신

2. **API 서버 (FastAPI)**
   - RESTful API 제공
   - 비동기 처리 (async/await)
   - 추천 로직 호출 (내부 또는 외부 서비스)
   - 인증/인가 처리 (JWT)

3. **데이터베이스 (PostgreSQL)**
   - `users`, `ingredients`, `recipes`, `user_ingredients`, `notifications` 테이블
   - 재료 이름 정규화 (예: "양파" vs "양파(1개)") → 추천 정확도 향상

4. **캐싱 계층 (Redis)**
   - 인기 레시피 캐싱
   - 사용자별 추천 결과 캐싱 (TTL: 1시간)
   - 유통기한 임박 알림 큐

5. **비동기 작업 (Celery + Redis)**
   - 매일 자정 유통기한 임박 재료 스캔 → 알림 생성
   - 추천 결과 배치 전처리 (향후 확장)

6. **배포 (Docker + AWS ECS 또는 Railway)**
   - CI/CD 파이프라인 자동화
   - 로그 및 메트릭 수집

## 🛠️ 기술 스택 기반 아키텍처 제안 (React Native + FastAPI + PostgreSQL)

| 계층 | 기술 | 역할 |
|------|------|------|
| 프론트엔드 | React Native | 크로스플랫폼 앱 개발 (iOS/안드로이드) |
| 백엔드 | FastAPI | 고성능 API 서버 (레시피 추천, 재료 관리) |
| DB | PostgreSQL | 사용자, 재료, 레시피, 유통기한 데이터 저장 |
| 추천 로직 | Python 기반 ML (예: 협업 필터링, 콘텐츠 기반 추천) | 사용자 재료 → 레시피 매칭 |

> ✅ **추천 로직 설계 방향**:
> - **콘텐츠 기반 필터링**: 재료 → 레시피 매칭 (예: "김치, 계란, 두부" → 김치찌개)
> - **사용자 행동 기반**: 자주 사용한 재료, 선호 요리 스타일 반영
> - **유통기한 기반 가중치**: 임박한 재료 우선 추천
